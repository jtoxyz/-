# 受付の係が支払い済みにする方式（スタッフ確定方式）設計

作成日: 2026-11-26

## 背景と目的

「自治会×がっけんぽ マグロ企画」で、受け取った現金と支払い済みの人数が約6人分合わなかった。

今の流れは次のとおり。

1. 係の画面に動的QRを出す。
2. 学生が自分のスマホで読み取る。
3. 学生がGoogleでログインする。
4. 学生の端末で支払い済みになる。

お金を受け取る人（係）と、支払い済みにする端末（学生のスマホ）が別になっている。

本番DBの記録では、**QRを読み取ったのにログインまで進まず確定しなかった読み取りが29件**あった。すぐ読み直した分を除いても十数回ある。現金を渡したあとに学生のログインが止まり、そのまま列を離れると、その人は払ったのに未払いのまま自動キャンセルされる。受付の係も学生も「操作が難しい」と感じていた。

目的は、**お金を受け取った係本人が、自分の端末でその場で支払い済みにする**こと。あわせて、受付を閉めるときに記録と現金を照合し、ずれをその日のうちに見つけられるようにする。

## 目標

- 支払い済みにする操作は、係の端末で係が行う。学生はログインもQRの読み取りもしない。
- 係は、学生の「自分の予約」画面に出るQRをスキャナーで読んで予約者を見つける。学籍番号で探す方法は作らない（利用者の判断。学生は大学の出席でスマホが必須で、予約サイトは大学メールでログインするため、どの端末でもQRを出せる）。
- 「だれが、いつ、いくら受け取ったか」を記録する。取り消しも記録する。
- 受付を閉めるときに、係ごとの「その日に受け取った件数・合計金額」を画面で出し、現金と照合できる。
- 起きやすいミス（押し忘れ、別人を押す、二重に押す、押し間違い）を画面とDBで防ぐか、すぐ気づけるようにする。

## やらないこと

- キャッシュレス決済（申請の手間が大きいため、利用者が除外）
- 専用のハンディターミナル（高すぎるため、利用者が除外）
- 数えた現金の額を入力して保存する機能（今回は照合の画面だけ。必要になれば次の段階で追加する）
- 学籍番号・氏名での検索（利用者が除外）。QRが出せない例外は、既存の管理画面の予約者一覧から管理者が処理する（その操作も記録に残る）
- 学生がQRを読む今の方式の削除（企画ごとに使うかどうかを選べるようにし、コードは残す）

## 失敗とみなすこと

- 係でない人が学生のQRを読んで、支払い済みにできてしまう。
- 同じ企画で2つの方式が同時に動き、どちらで処理したか分からなくなる。
- 押し間違いを取り消したときに、記録が消えて照合できなくなる。

## 前提と制約

- 受付は基本1〜2人。端末は係が持っているノートパソコンを使う（この大学は学生全員がノートパソコンを持っている）。そこに2Dスキャナー（スマホ画面対応、USBでキーボードとして認識されるもの）を1台ずつつなぐ。買うのはスキャナーだけ。
- 受付の場所は学生会館で、電波の問題は考えない（利用者の判断）。
- 権限の判定は既存の `can_operate_event(event_id)` を使う（管理者、またはその企画の担当スタッフ）。
- 金額は券種の `event_ticket_options.price_yen` から取る。
- AGENTS.md の規則に従う。主なものは次のとおり。
  - 管理者・スタッフ用のRPCは anon に公開しない。関数の中でも権限を確認する。
  - 日時の表示には `Asia/Tokyo` を明示する。
  - 本番DBに反映したら、同じ内容を migration に入れる。
  - 新しい列は、フロント側では任意の項目として扱う。

## 検討した方式

| 案 | 内容 | 評価 |
|---|---|---|
| A | 係が学籍番号で探し、「受け取った」を押す | 費用は0円。1人あたり数秒の入力がかかる |
| **B（採用）** | 学生の予約画面に出すQRを、係がスキャナーで読む | 費用はスキャナー代だけ。速い。学籍番号の入力は付けない（利用者の判断） |
| C | 今の方式のまま、係の画面に「今払い済みになった人」を出す | 学生のログイン失敗という原因が残るため、不採用 |

Bを選んだ理由は、今の管理画面で係が予約者を探して支払い済みにできることを、受付向けに速く安全にしたものだからである（利用者の判断）。

## 設計

### 1. 企画ごとの方式の切り替え

- `events.payment_confirm_mode text not null default 'student_scan' check (in ('student_scan','staff'))` を追加する。
- `'staff'` の企画では次のようにする。
  - 係の画面（`/staff`）と管理画面では、支払いQR（動的・1日）のタブを出さず、「支払い受付」を出す。
  - `claim_payment_qr` と `redeem_payment_qr` は、その企画のQRなら「この企画では受付の係が支払いを確認します」というエラーを返す。2つの方式が混ざるのを防ぐためである。
  - 学生の「自分の予約」画面には「受付で見せるQR」を出し、受付のQRを読むボタンは出さない。
- 企画の編集画面に切り替えを追加する。既存の企画の動きは変えない（既定値が `student_scan` のため）。

### 2. 記録（新しいテーブル `payment_receipts`）

1回の受け取りや取り消しを、1行ずつ追記していく。照合と監査に使う。

| 列 | 内容 |
|---|---|
| id | uuid |
| event_id | 企画 |
| reservation_id | 予約 |
| action | `'received'` または `'undone'` |
| amount_yen | その時点の券種の金額（券種がなければ0） |
| operator_user_id | 操作した人（auth.uid()） |
| operator_name | 操作した人の表示名（staff_members.display_name。管理者ならメールなど） |
| created_at | timestamptz |

- RLSを有効にし、直接読み書きするポリシーは作らない。読み書きはRPCだけで行う（security definer）。
- `reservations.payment_status / paid_at / payment_confirmed_by` は今までどおり更新する。既存の一覧・Excel出力・自動キャンセルはそのまま動く。

### 3. RPC（すべて authenticated だけに実行を許可し、関数の中で `can_operate_event` を確認する）

- `staff_find_payment_target(p_event_id uuid, p_query text) -> jsonb`
  - `p_query` はQRの中身（後述のURL、または `public_token` だけ）。前後の空白は無視する。学籍番号や氏名では探さない。
  - その企画の `status = 'reserved'` の予約から、該当者の予約をすべて返す。
    - 返す項目：予約ID、氏名、学籍番号、券種名、金額、開催枠、支払い状態、支払い期限、受領した時刻と受領した人の名前
  - 見つからなければ `not_found` を返す。期限切れ（`expired`）やキャンセル済みしかなければ、その状態を返す。
- `staff_receive_payment(p_reservation_ids uuid[]) -> jsonb`
  - 対象を行ロックし、`payment_status = 'pending'` のものだけを `paid` にする。1件ずつ `payment_receipts` に `received` を記録する。
  - すでに `paid` のものは更新せず、`already_paid` として、いつ・だれが受領したかを返す。二重に押しても記録は増えない。
  - 結果として、件数と合計金額を返す。
- `staff_undo_payment(p_reservation_id uuid) -> jsonb`
  - スタッフは、**自分が今日（Asia/Tokyo）受領した分だけ**取り消せる。管理者はいつでも誰の分でも取り消せる。
  - 予約を `pending` に戻し、`undone` を記録する。
  - その時点で支払い期限が過ぎていても、すぐには自動キャンセルしない。期限の扱いは既存の自動キャンセル処理に任せる。この点は実装時に確認する。
- `staff_get_payment_summary(p_event_id uuid, p_date date default 今日) -> jsonb`
  - その日の受領と取り消しを、操作した人ごとに集計して返す。返す項目は、件数、合計金額、明細（時刻、氏名、学籍番号、券種、金額、受領か取り消しか）。
  - スタッフには自分の分だけ、管理者には全員の分を返す。

### 4. 学生の「受付で見せるQR」

- `'staff'` の企画で `payment_status = 'pending'` の予約には、「自分の予約」（MyTicketsList）に大きなQRを出す。タップすると全画面で表示する。既存の全画面表示と同じ作りにする。
- QRの中身は、係の画面のURLに予約の識別子を付けたものにする。例：`https://<サイト>/staff/receive?r=<public_token>`
  - 係が普通のカメラアプリで読んでも、係の画面が開いて処理を続けられる。
  - 係でない人が読んでも、係の画面が開いて「権限がありません」と出るだけで、何も変わらない。
  - `public_token` は既存のチケット画面のURLにも使っている値である。QRにすると見られる範囲が少し広がるが、チケット画面はもともと公開URLで見られるものなので、実質的に変わらないと判断した。

### 5. 係の画面「支払い受付」（`/staff` のタブ、および `/staff/receive`）

```
┌──────────────────────────────┐
│ 自治会×がっけんぽ マグロ企画     [係：山田]  │
│ ┌─────────────────────┐ [📷読む]   │
│ │ QRをスキャナーで読んでください │          │
│ └─────────────────────┘            │
│                                          │
│  田中 太郎   s23x123                      │
│  券種：大トロ付き   ¥1,500                 │
│  枠：11/18 12:00-12:30                     │
│  ┌──────────────────────────┐    │
│  │   ¥1,500 受け取った               │    │
│  └──────────────────────────┘    │
│                                          │
│ 今日の受付：32件  ¥41,500   [照合を見る]  │
│ 直前：佐藤 花子 ¥1,000 受領 12:31 [取消]   │
└──────────────────────────────┘
```

- 入力欄は画面を開いたときと処理のあとに自動でフォーカスし、スキャナーの入力（文字＋Enter）をそのまま受け取る。手で打った学籍番号などは受け付けない。
- 予備として、係のスマホで同じ画面を開いたときに使えるカメラ読み取りのボタンを付ける。既存の `PaymentQrScanButton` の読み取り部分を部品として切り出して使い回すので、追加の手間は小さい（Claudeの判断）。
- 見つかった人の表示は状態ごとに分ける。
  - **未払い**：氏名・学籍番号・券種・金額を大きく出し、「¥金額 受け取った」ボタンを出す。同じ人に未払いが複数あれば、合計金額で一度に受領する。
  - **支払い済み**：赤の帯で「〇時〇分に〇〇さんが受領済み。受け取らないでください」と出す。ボタンは出さない。
  - **期限切れ・キャンセル済み**：その旨を出す。受領はできない。管理者に回す。
  - **見つからない**：「この企画の予約が見つかりません」と出す。
- 受領したら緑の帯で「受領しました ¥1,500」を出し、入力欄を空にして次の人を待つ。
- 画面の下に、今日の自分の件数と合計、直前の数件を出す。直前の分には「取消」ボタンを付け、押すと確認ダイアログを出す。
- 「照合を見る」では、その日の明細と合計を出す。受付を閉めるときに現金と比べる。管理者は全員分を見られ、日付を変えることもできる。
- 同じQRを続けて2回読んでも、2回目は「支払い済み（今あなたが受領）」と出るだけにする。

### 6. 管理画面

- 企画の編集に「支払いの確認方法：学生がQRを読む／受付の係が確認する」を追加する。
- 支払い管理（payment-management）に、日付ごと・係ごとの受領件数と合計を出す。中身は `staff_get_payment_summary` の管理者用の結果を使う。
- 既存の「管理画面から支払い済みにする」（`admin_set_reservation_payment_status`）も、`payment_receipts` に記録するよう変更する。照合の合計がずれないようにするためである。

## 利用者が決めたこと

- キャッシュレスにはしない。
- 専用のハンディターミナルは買わない。
- 案Bにする（学生のQRを係が読み、係が確定する）。
- 学籍番号で探す方法は作らない。
- 受付は1〜2人。端末は係のノートパソコン。買うのはスキャナーだけ。

## 私（Claude）が決めたこと（確認してほしい点）

- 企画ごとの切り替えにする。既定は今の方式のままで、マグロ企画のような企画は「受付の係」に切り替える。
- スタッフが取り消せるのは、自分がその日に受領した分だけにする。それ以外の取り消しは管理者が行う。
- 学生のQRの中身は、係の画面のURLに `public_token` を付けたものにする。
- 数えた現金の額を入力・保存する機能は、今回は作らない。照合の画面だけにする。
- 支払いに来る時間枠（payment_visit_slot）が決まっている企画では、係の画面にその枠も出す。枠の外に来た人も受領はできるようにし、ブロックはしない。
- 管理画面から予約を作ると同時に支払い済みにする場合（`admin_create_reservation_for_user`）も、`payment_receipts` に記録する。

## 実装で決めること

- 各RPCの返り値の細かい形と、エラー文
- 入力欄の自動フォーカスと、スキャナー入力の扱い（Enterで検索）
- `/staff/receive` を独立したページにするか、`/staff` のタブにクエリで切り替えるか
- Excel出力（`reservationExport.ts`）に受領者の列を足すかどうか

## 確認とリリース

- テストで予約を作るときは、トランザクションの中で行い、最後にロールバックする。
- 確認すること：
  - 係でない人のRPC呼び出しが拒否されること
  - 二重に受領しても記録が1件になること
  - 取り消しが記録に残ること
  - `'staff'` の企画では学生のQR方式が拒否されること
- Supabase Security / Performance Advisors を確認する。
- DBへの反映を先に済ませてから、フロントをmainにマージする（AGENTS.md）。
